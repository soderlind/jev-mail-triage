# macOS app with a bundled Python helper

The macOS app is a SwiftUI menu bar shell; all mail access, classification, database writes and move policy stay in the Python engine, shipped inside the app as a PyInstaller onedir helper (`Contents/Helpers/JevMailTriageHelper.app`) so users need no Python install. The UI talks to the helper only by launching it with an argument array (`rpc`) and exchanging one versioned JSON request and response over stdin/stdout, with diagnostics on stderr and distinct exit codes; there is no localhost server and no shell interpolation. Background triage is the same helper binary running `worker` as a LaunchAgent registered through `SMAppService`, so it runs independently of windows, needs no privileges, and goes through macOS background item approval. The UI reads the worker's status file and writes a pause/reload control file through the helper; the existing database lock remains the single-worker guarantee, including against the legacy `com.soderlind.jev-mail-triage` agent, which the app detects and replaces only after an explicit migration action.

The helper binary owns the Keychain items (service `jev-mail-triage`, accounts `bridge:<id>` and `typesafe-api-key`) via `keyring`. The UI never reads secret data: it checks presence with an attributes-only, non-interactive query and sends new values to the helper on stdin (`secrets.set`). Because the rpc helper and the background worker are one signed executable, they share one Keychain ACL entry and the worker never prompts. Items created by the legacy Homebrew Python install are re-written by the helper during migration (`secrets.adopt`), which prompts once per item; ad-hoc development builds change their code signature on every build and so may prompt again. This was chosen over a shared access group, which needs a provisioning profile and data-protection Keychain items that the CLI's `keyring` backend does not use.
